# Техническое задание на разработку информационной системы «Культурный след»

Версия: черновик первого модуля.  
Тема: расчёт индекса культурного влияния на основе цитирований.  
Текущий реализуемый этап: лабораторная работа № 1.

## 1. Цель

1.1. Цель разработки — создать информационную систему для публикации отрывков произведений искусства и последующего расчёта условного индекса культурного влияния произведения или автора на основе количества упоминаний, референций и прямых цитирований в других работах.

1.2. Для расчёта планируется использовать прозрачную учебную формулу:

`I = M + 2R + 3C`,

где `M` — количество упоминаний, `R` — количество референций, `C` — количество прямых цитирований, `I` — условный индекс культурного влияния.

1.3. Значение индекса является условной учебной оценкой и не претендует на роль научно утверждённого библиометрического показателя.

## 2. Назначение

2.1. Система предназначена для просмотра отрывков литературных произведений и киносценариев, поиска отрывков по предметным данным и оформления заявок на расчёт индекса культурного влияния.

2.2. Гость просматривает опубликованные отрывки, фильтрует их и открывает выбранный отрывок в ленте.

2.3. Создатель заявки после регистрации и аутентификации формирует заявку из выбранных отрывков, подтверждает её и просматривает свои заявки.

2.4. Модератор просматривает заявки пользователей и изменяет их состояние в соответствии с предусмотренным бизнес-процессом.

2.5. В лабораторной работе № 1 реализуется только гостевая часть с серверным HTML: лента, страница добавления без сохранения и плитка карточек. Регистрация, заявки, роли, база данных и расчёт индекса относятся к следующим этапам.

## 3. Задачи разработки

3.1. Разработать мобильный дизайн трёх страниц и базовое серверное приложение на TypeScript, NestJS и Handlebars; хранить данные лабораторной № 1 в массиве, а изображения и видео — в MinIO.

3.2. Спроектировать PostgreSQL-базу данных и подключить её к NestJS через TypeORM; реализовать работу с отрывками и их статусами.

3.3. Разделить серверную часть на предметные слои, реализовать операции с заявками и связью заявок с отрывками в соответствии с требованиями лабораторной № 3.

3.4. Реализовать регистрацию, аутентификацию, разграничение прав, хранение сессий в Redis и документацию API в Swagger.

3.5. Разработать гостевую часть одностраничного приложения на React, TypeScript и React-Bootstrap с тестовыми данными.

3.6. Подключить React-приложение к веб-сервису и реализовать поиск похожих материалов с использованием CLIP и `transformers.js`.

3.7. Реализовать интерфейсы создателя заявки и модератора с Redux Toolkit, асинхронными действиями и клиентом Axios, сгенерированным по Swagger.

3.8. Добавить адаптивность, хранение состояния фильтров и возможность установки приложения как PWA.

3.9. Создать настольное приложение на Tauri для гостевого интерфейса и подключить его к веб-сервису по адресу локальной сети.

3.10. Разместить демонстрационную версию фронтенда с тестовыми данными на GitHub Pages.

3.11. Подготовить UML-диаграммы, техническое задание и расчётно-пояснительную записку.

3.12. Вести исходный код в Git и хранить результаты каждой лабораторной работы в отдельной тематической ветке удалённого репозитория GitHub.

## 4. Функциональные требования

### 4.1. HTTP-методы веб-сервиса

4.1.1. В лабораторной работе № 1 сервер должен обрабатывать ровно три вида GET-запросов:

- `GET /artwork-excerpts/feed/:id?next=true` — открыть опубликованный отрывок по идентификатору; при `next=true` открыть следующий опубликованный отрывок;
- `GET /artwork-excerpts/draft` — получить единственный отрывок со статусом `draft` для страницы добавления без сохранения;
- `GET /artwork-excerpts?publicationYear=...` — получить плитку опубликованных отрывков с необязательной серверной фильтрацией по году публикации.

4.1.2. Тот же обработчик ленты допускает путь `GET /artwork-excerpts/feed` без идентификатора для перехода из нижней навигации; он открывает первый опубликованный отрывок.

4.1.3. На последующих этапах должны быть добавлены методы регистрации и аутентификации, создания, публикации и логического удаления отрывка, создания и изменения заявки, управления связью заявки с отрывками, получения списка заявок и изменения состояния заявки модератором. Их окончательные URL, тела запросов и коды ответов фиксируются в таблице методов веб-сервиса после реализации лабораторных работ № 2–4.

### 4.2. Меню

4.2.1. На всех трёх страницах лабораторной № 1 должна находиться нижняя панель навигации с пунктами «Лента», «Добавление» и «Плитка».

4.2.2. В итоговом React-приложении меню должно дополнительно предоставлять переходы к регистрации, аутентификации, текущей заявке и списку заявок с учётом роли пользователя.

### 4.3. Окно регистрации гостя

4.3.1. Гость должен иметь возможность ввести регистрационные данные и отправить их серверу.

4.3.2. После успешной регистрации пользователь получает возможность аутентифицироваться как создатель заявки.

4.3.3. Окно относится к следующим лабораторным работам и не входит в реализацию лабораторной № 1.

### 4.4. Окно аутентификации гостя

4.4.1. Гость должен иметь возможность ввести учётные данные и начать пользовательскую сессию.

4.4.2. Сервер должен проверять учётные данные, сохранять сессию в Redis и учитывать роль пользователя при выдаче доступа.

4.4.3. Окно относится к следующим лабораторным работам и не входит в реализацию лабораторной № 1.

### 4.5. Окно списка отрывков

4.5.1. Гость должен видеть опубликованные отрывки в виде плитки из двух столбцов.

4.5.2. Для карточки должны отображаться собственное изображение, название произведения и количество лайков, вычисленное сервером как длина массива идентификаторов пользователей.

4.5.3. Гость должен иметь возможность отфильтровать список по году публикации. Фильтрация выполняется на сервере, а введённое значение сохраняется в поле после ответа.

4.5.4. Нажатие карточки должно открывать ленту с идентификатором выбранного отрывка.

4.5.5. Черновик и логически удалённые записи в плитке не отображаются.

### 4.6. Окно одного отрывка

4.6.1. Гость должен видеть вертикальное автоматически проигрываемое без звука видео, изображение, название произведения, текст отрывка, автора, год публикации и количество лайков.

4.6.2. Информация и элементы управления должны располагаться поверх видео.

4.6.3. Гость должен иметь возможность раскрыть и свернуть описание средствами HTML без клиентского JavaScript.

4.6.4. Кнопка «Следующий» должна отправлять GET-запрос с параметром `next=true` и открывать следующий опубликованный отрывок.

4.6.5. Удалённые записи не должны быть доступны через интерфейс.

### 4.7. Окно заявки создателя

4.7.1. Аутентифицированный создатель должен иметь возможность добавить отрывок в заявку, изменить предусмотренное количество, удалить отрывок из черновика заявки и подтвердить заявку.

4.7.2. Для подтверждённой заявки редактирование состава должно быть запрещено.

4.7.3. После обработки должны отображаться исходные показатели `M`, `R`, `C` и рассчитанный результат `I = M + 2R + 3C`.

4.7.4. Окно относится к следующим лабораторным работам и не входит в реализацию лабораторной № 1.

### 4.8. Окно списка заявок

4.8.1. Создатель должен видеть только собственные заявки и переходить к просмотру выбранной заявки.

4.8.2. Модератор должен видеть все заявки, фильтровать их по диапазону даты формирования и статусу и выполнять разрешённые переходы состояний.

4.8.3. Проверка прав доступа должна выполняться сервером, а не только скрытием элементов интерфейса.

4.8.4. Окно относится к следующим лабораторным работам и не входит в реализацию лабораторной № 1.

## 5. Требования к аппаратному обеспечению

5.1. Серверная часть должна запускаться на компьютере архитектуры x86-64 с доступом к локальной сети.

5.2. Для учебного локального запуска рекомендуется не менее двух процессорных ядер, 8 ГБ оперативной памяти и 10 ГБ свободного места для исходного кода, контейнеров и медиафайлов.

5.3. Клиенту требуется компьютер или мобильное устройство с современным браузером, экраном шириной от 360 пикселей и сетевым подключением к серверу.

5.4. Итоговый расчёт числа ядер, оперативной памяти и дискового пространства по количеству пользователей, RPS и пятилетнему приросту базы данных должен быть выполнен после утверждения нагрузки и структуры таблиц. Приведённые в пункте 5.2 значения являются требованиями для разработки, а не результатом нагрузочного расчёта.

## 6. Требования к программному обеспечению

6.1. Сервер разработки: операционная система Windows 10/11 либо Ubuntu 22.04; актуальная LTS-версия Node.js, совместимая с выбранной версией NestJS; npm; NestJS; TypeScript; Handlebars.

6.2. Хранилища итоговой системы: PostgreSQL, MinIO и Redis, запускаемые в Docker-контейнерах; точные версии образов должны быть закреплены в `docker-compose.yml` перед оформлением окончательной версии ТЗ.

6.3. Доступ к PostgreSQL должен выполняться через TypeORM там, где задание требует ORM, и через явный SQL-запрос там, где это отдельно установлено заданием.

6.4. Клиент итоговой системы: современная версия Google Chrome, Microsoft Edge или Mozilla Firefox с поддержкой HTML5, CSS3 и JavaScript; для SPA — React, TypeScript, Redux Toolkit, Axios и React-Bootstrap.

6.5. Для разработки требуются Git, Docker Desktop или Docker Engine, редактор исходного кода, Figma и StarUML.

6.6. Точные номера версий необходимо перенести из фактически зафиксированных `package.json`, lock-файла и `docker-compose.yml`; указывать непроверенные номера версий в окончательном ТЗ нельзя.
