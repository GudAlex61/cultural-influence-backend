# Контрольные вопросы ЛР 4

**Cookie.** Небольшой набор данных, который сервер передаёт браузеру в `Set-Cookie`; браузер посылает его обратно в `Cookie`. В ЛР 4 cookie `sessionId` содержит случайный идентификатор, а не пароль или данные пользователя. `HttpOnly` закрывает доступ JavaScript, `SameSite=Lax` ограничивает межсайтовую отправку, `Secure` включается при HTTPS.

**Сессия.** Серверное состояние между HTTP-запросами. После проверки пароля сервер создаёт случайный ID и кладёт в Redis ключ `session:<ID>` со значением ID пользователя и временем жизни. Запрос с действительным cookie определяет пользователя по этому ключу. Выход удаляет ключ.

**Redis.** Быстрое хранилище «ключ — значение» в памяти. Здесь оно хранит сессии с TTL; PostgreSQL остаётся постоянным хранилищем пользователей, отрывков и лайков. Проверка: `docker exec cultural_redis redis-cli GET session:<ID>` и `TTL session:<ID>`.

**JWT.** Подписанный токен с утверждениями о пользователе; сервер проверяет подпись без обращения к хранилищу на каждом запросе. Удалить действующий JWT немедленно сложнее без списка отзыва. В этом проекте JWT не используется: по требованиям NestJS ЛР 4 выбран серверный сеанс в Redis и cookie.

**Аутентификация и авторизация.** Аутентификация устанавливает личность по имени и паролю (`POST /api/sessions`). Авторизация проверяет, можно ли выполнить действие: `SessionGuard` требует сеанс для изменения данных, а сервис публикует и удаляет только запись её создателя. Публичные GET доступны гостю.

**SSO.** Single Sign-On — единый вход, после которого пользователь получает доступ к нескольким приложениям через общего поставщика идентификации. У нас SSO не реализован: логин относится только к «Культурному следу».

**Двухфакторная аутентификация.** Проверка двух независимых факторов, например пароля и одноразового кода из приложения. Это повышает защиту при утечке пароля. В ЛР 4 не требуется и не реализована.

**RSA.** Асимметричный алгоритм: открытый ключ используют для проверки подписи или шифрования, закрытый — для подписи или расшифрования. В HTTPS RSA может применяться в сертификатах и подписании, но симметричный ключ сеанса обычно согласуется отдельно. Наши пароли хешируются `scrypt`, а ID сессии генерируется криптографически случайно; RSA в API не используется.
